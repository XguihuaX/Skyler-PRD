## 优先级与证据缺口

1. 当前版本实测完整启动各 boot mark、首帧和 appReady 时间；当前 MCP clients init 已有预热后交替对照，但 MCP session manager 与模型预热仍需一同测量。
2. 采集当前真实对话的 `_build_messages`、embedding encode、LLM 首字和总耗时分布，再判断值得优化的热点。
3. 固定一组真实任务和 MCP 配置，对工具 schema 的 Token 成本及任务成功率做对照，再考虑按任务筛选。
4. 真机连续语音验收：正常播完、连续分段、打断、切模型、关闭画布；同时记录空闲/播放 CPU、内存和口型帧稳定性。
5. 真机测量首帧、脚本解析及设置/能力面板首次打开耗时，验证延迟加载的体感；Live2D 真正就绪后才通过 appReady gate。

本批没有测量真实用户设备的帧时间、内存或当前版本**完整**启动速度，不能宣称这些指标已改善。若某问题修改后连续两轮验证仍存在，按用户规则回退该问题的改动并跳过，避免反复试错。

## 验证说明

- MCP 并行启动的集成回归覆盖准备并发、按配置顺序进入 `ToolRegistry.list_schemas()`、单 client 失败继续、取消启动释放等待门、holder 关闭清理。两份旧 MCP pytest 文件已补齐异步 fixture/测试标记和别名表迁移准备；受影响路径合跑使用 `pytest -o asyncio_mode=auto` 为 72/72 通过。三个历史脚本按其自带 runner 分别为 35/35、29/29、24/24 通过。
- `tests/test_mcp_client.py` 旧脚本原为 23/28 通过；5 项失败在当前基线代码中已经存在：4 项仍按旧的非 holder 生命周期断言，1 项要求旧版精确 DTO key 集。已移除被新 holder 集成测试覆盖的旧断言，并改为检查 DTO 必需字段；脚本现为 24/24 通过。
- 前端 `npm run build` 成功并产出独立的次要界面 chunk。首次打开显示加载提示；需真机检查切换页、打开浮层、关闭后重开与 Live2D 就绪。
