# INV-24 · 记忆检索与工具选择现状

日期：2026-10-11。性质：代码与本机数据调查、下一批验证方案；不代表功能已修改或真机验收完成。

## 现有链路

| 层 | 当前实现 |
| --- | --- |
| 近期对话 | `backend/memory/short_term.py` 按 `(user_id, character_id, conversation_id)` 保留约 4,000 Token 的近期原文；更早原文留在 `chat_history`。 |
| 会话摘要 | `backend/memory/summary.py` 按会话滚动压缩，有独立 pointer 和预算；空摘要不注入。 |
| 长期事实 | `backend/memory/extractor.py` 定时读取新 user turn，经 LLM、质量过滤、去重后入 `memory`，记录来源 turn、置信度和类型；用户显式要求记住时另有 `save_memory` 工具。删除持久事实有 tombstone 防止再次写回。 |
| 召回 | `backend/memory/long_term.py` 对达到长度门槛的用户输入编码，读取该用户所有有效记忆并计算相似度与遗忘曲线分数，取 Top 5；`chat._build_messages` 将结果与画像、活动、摘要、近期原文一起组装。 |
| 工具 | `chat._get_all_tools()` 每轮把 `MEMORY_TOOLS + ToolRegistry.list_schemas()` 全部交给 LLM；工具执行仍由后端分发和权限门负责。`prompt/tool_addendum.py` 另有约 14 KB 的常驻自然语言工具说明。 |

本机 `momoos.db` 只读统计：长期记忆 15 条，均有 embedding、来源 turn 和置信度；会话摘要表 20 行，当前文本均为空。最后一次记忆行日期为 2026-08-09，不能据此推断当前线上或真机的召回质量。结构性内存契约测试在隔离 SQLite 进程中通过（`pytest -q tests/test_memory_contract.py`，1/1）；它不测真实对话的正确召回率。

## 已确认的边界与风险

1. **提取失败会丢失重试机会。** `call_extraction_llm()` 在 LLM 异常时返回 `None`，`_process_user_turns()` 随即返回，但 `_extract_batch()` 仍推进 `last_processed_turn_id`。现有 E2E 测试明确把它作为“避免卡住”的策略，因此这是有意的可靠性取舍；代价是该批 turn 不再自动重试。后续应限定重试次数，再记录失败批次供修复或人工重放，而不是无限卡住或静默跳过。
2. **短输入与泛化检索。** 当前配置对少于 10 字的输入直接跳过长期召回；“上次那件事”这类跨会话短指代可能落空。达到门槛的普通长输入又会尝试 Top 5，即使近期上下文已足够。应先做检索路由，并用旧对话指代、普通闲聊、当前事实等样本量化命中率与无关召回率。
3. **范围与冲突。** 当前聊天长期记忆检索只传 `user_id`，这是既定的跨角色共享用户事实策略；`character_id` 主要留作来源标记。若未来保存角色私有经历，需要独立 scope 与读取约束。F-007 只处理有显式 `claim_key` 的冲突，不对自由文本做语义矛盾合并；相似度去重也不等于新事实覆盖旧事实。
4. **规模成本。** 长期检索每轮读取该用户所有有效记忆后逐条打分；提取器做重复检测时对候选与已有记忆文本逐条编码。当前 15 条不证明需要向量索引，但量增大时应先测延迟，再考虑复用库中已有向量、分层过滤或索引。
5. **工具说明与实际能力有漂移风险。** `tool_addendum.py` 仍写“屏幕写工具不可见”，但本机 macos-use 配置/状态调查显示部分写工具可注册并经过确认门（见 `INV-17`）。每轮还同时发送全部可见工具 schema 和长篇静态说明，部分信息重复。历史跨版本探针的工具 schema 中位数为 9,423 Token；当前直接导入仅 5 个 schema/731 Token，不能把历史值当成当前每轮成本。

## 建议的职责分配

- **Prompt**：保留短而稳定的角色、行为和权限原则，以及这一轮的任务目标；不把所有记忆正文和所有工具操作手册长期写入。
- **结构化存储**：用户稳定偏好、带来源和有效期的事实；提醒、待办、邮件草稿等有状态任务使用各自的数据表/外部系统，不把“待完成”只写成自然语言记忆。
- **检索路由**：先判断近期上下文是否已足够；旧事走记忆检索，文档问题走授权文档检索，实时事实走工具。召回结果带来源、时间和范围，只注入少量足以回答的证据。
- **工具注册与选择**：后端 registry/schema 描述参数和返回值；路由层按任务给模型一个较小的可用工具集合，低置信度时扩展搜索。实际权限、参数验证、确认与执行结果都由代码负责。复杂多步任务需保存步骤状态并在每次动作后核验。
- **质量门**：先固定代表性任务和当前已启用工具集合，比较任务完成率、错用工具率、误召回/漏召回、输入 Token、首字和总耗时，再决定是否默认启用按需加载。

这与 [OpenAI Function calling 指南](https://developers.openai.com/api/docs/guides/function-calling)关于清晰 schema、把可确定的参数交给代码、减少初始工具数并评估的建议一致；[Tool search 指南](https://developers.openai.com/api/docs/guides/tools-tool-search)给出延迟加载工具的机制。但本项目经 LiteLLM 接多供应商，不应直接假定某一供应商的 `tool_search` API 可用；可先在本项目路由层实现同样的选择原则。检索元数据先过滤、再做语义搜索也有 [Retrieval 指南](https://developers.openai.com/api/docs/guides/retrieval)的对应实践。

## 下一批最小验证

1. 在隔离库里模拟提取 LLM 暂时失败、随后恢复：确认现状会漏提，再设计“有限重试 + 可重放记录”并验证不会重复写入。
2. 准备不少于三类固定用例：近期指代、跨会话旧事、实时工具请求；量化误召回和漏召回，再决定短输入门与检索路由。
3. 记录一次当前完整启动后的真实 schema 集合和输入 Token；对比全量暴露与任务族选择的成功率及成本。包括权限关闭、工具不可用、误分类后的回退。
4. 清理与真实工具状态冲突的 prompt 文案时同步测试确认门，不通过删文案来改变权限或可见能力。

用户暂时无法真机验收；以上均可先做隔离自动验证。需要改变模型可见工具集合的实现应在固定任务质量对照后进行。
