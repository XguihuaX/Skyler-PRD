## 1. 背景与目标

2026-10-13 用户确认：**先自用，但按商业产品质量建设**。当前围绕用户自己的日常事务，建立可靠执行、失败恢复、资源与费用预算、数据可控及可维护性；多人市场验证、付费运营和对外发行不作为本阶段前置条件。四项质量调研与候选验证方案见 [INV-25](../INV-25-commercial-assistant-research.md)，其中建议不自动替代既有排期。

2026-10-23 更新调研见 [INV-28 四方向修改大纲](../INV-28-assistant-upgrade-research-outline.md)：以本机 M2/8 GB 为资源基线，细化日常场景发现、中文记忆检索与来源、上下文/费用、语音和 MaiBot/Hermes 借鉴。日常事务仍需与用户共同选择，邮件只是候选；文中的批次是建议，选定后再转入实施排期。

用户希望 Momo 从以对话和角色表现为主，转向能在授权范围内完成日常任务的个人电脑助手，同时保留自然、有人设的互动。此前提到的邮件总结与回复、闹钟和备忘录、连接其他 LLM、连续操作网页或桌面，都是说明方向的**例子**，不是已确定的首批功能或开发顺序。

任务 1 首先要与用户对接，找出他实际想让 Momo 帮忙的日常事务、当前做法和痛点，再共同选择首批功能。选定场景后，才为每项功能写具体需求和验收标准，并安排实现。

## 2. 任务 1 的工作与产物

1. **需求访谈**：请用户讲述近期真实发生的任务，而不只请他从预设功能清单中选择。逐项了解发生频率、耗时、当前工具、最烦的步骤、期望 Momo 做到哪一步。
2. **场景与能力清单**：将用户叙述整理为「触发条件 → 读取哪些信息 → 判断或操作 → 结果如何交付」的任务流程。标出所需应用或账户、已有能力、缺口和依赖；邮件、日历、文件、浏览器、桌面应用、消息等仅作为可能的来源。
3. **权限与交互选择**：与用户明确哪些步骤可自动执行、哪些要先展示草稿或请求确认；沟通提醒方式、打扰程度、隐私范围、失败后的处理，以及期望的人设表达。
4. **共同排优先级**：按用户价值、使用频率、实现与维护成本、权限风险、现有基础，提出首批候选场景及取舍。向用户复述理解，记录其选择和仍未决定的问题；未经这一步，不把研究示例写成既定排期。
5. **形成可实施需求**：为选定的每个场景单独写清用户故事、范围、界面与数据来源、成功/失败状态、验收用例。先交付一条可核验的端到端任务，再扩大自动化范围。

本任务的首批产物是**访谈记录、场景清单、优先级与待决策项**。功能 PRD 和实施切片在用户确认具体场景后补充；本草案本身不代表已选定功能。

## 3. 供访谈讨论的候选场景

- 信息整理：例如邮件、日历、消息、网页或文件的摘要、检索和待处理事项。
- 时间管理：例如提醒、备忘、闹钟、日程准备和后续跟进。
- 内容与操作：例如起草回复、整理文件、填写网页或跨应用完成一个任务。
- 模型与交互：例如切换模型、语音沟通、主动提出建议、按场景调整角色表达。

这些场景用于帮助用户想起需求，可以增加、合并或删除。某个领域被提及，不代表其子功能都要做；「邮件」尤其只是候选领域之一。

## 4. 通用产品原则（待具体场景细化）

- **任务状态真实**：Momo 能说明已读取什么、做过什么、下一步是什么；完成状态以外部系统或本地任务记录为准。失败、取消和部分完成要说清楚。
- **来源可核验**：引用外部信息时保留来源入口；不能把模型推测写成已发生的事实或已完成的操作。
- **权限按任务限定**：读取、起草、写入、对外发送等动作分别界定授权范围。发送、购买、删除、发布等高影响动作需要明确确认。
- **自然但不打扰**：角色表达服务于任务，可依据情境调整时机和措辞；不得因此漏掉用户明确要求的结果。
- **结果可追溯**：可撤销的操作提供撤销途径；关键操作记录输入、权限、执行结果和失败原因。结构化任务不以聊天记录或角色记忆作为唯一存储。

## 6. 验收与待决定事项

需求发现完成的标准：用户能看到完整的候选场景清单、自己最在意的任务、首批选择及理由、明确暂缓的内容和未解决的问题；这些选择经过用户核对。单项功能实施时再记录真实任务、输入与权限、过程状态、成功条件、失败恢复、自动检查和真机验收结果。

首轮访谈需要了解：最常遇到的三类日常任务是什么；希望 Momo 主动提醒还是等指令；常用应用和数据在哪里；愿意授权哪些读取及操作；怎样的结果能让用户认为「确实帮上忙」。邮箱服务、提醒投递方式、目标应用和默认模型只在对应场景被选中后决策。
