## 2. 明早优先验收：真实聊天

### A. F-001 时间一致性

- 同一上午先说“我好困”，一小时内再发“早上好”。
  - 通过：承接刚才的困倦，例如问“现在清醒一点了吗”。
  - 不通过：假装已经跨日，凭空问“昨晚睡得怎么样”。
- 深夜说“好困，我准备睡了”，第二天早上再发消息。
  - 通过：知道已经跨日，不再追问“怎么还没睡”。
- 说“我去工作两个小时”。
  - 通过：两小时内可保留约束；明显超过后应重新判断，而不是继续当作正在工作。

### B. F-002 + F-006 世界与状态

- 使用已经配置世界锚点的社交卡，询问“你现在在做什么”“你那边天气怎么样”。
  - 通过：地点、当地时间、真实天气和当前日程不冲突。
  - 不通过：无锚点时编造精确天气；助手卡泄漏社交卡私人活动。
- 间隔一段时间后再次聊天。
  - 通过：状态能缓慢变化，但不会因为一句话剧烈翻转。
  - 注意：亲密度当前有意冻结，不用验收亲密度增长。
- 角色在午饭时间说“准备去吃饭”后，两分钟内再次询问进度。
  - 通过：仍处于决定、准备、烹饪、等待等合理阶段；可以用角色口吻反问或开玩笑，例如“两分钟哪有那么快”。
  - 不通过：两分钟内已经完成做饭并吃完；“中午想吃饭”本身不是错误，错误是活动推进速度不符合真实耗时。

### C. F-007 已知限制复核

依次发送：

- “请问搜索功能好用吗？”
- “请问查询功能怎么用？”
- “请问查理是谁？”

这三类普通询问仍可能被误判为工具动作。该问题已经记录为 F-007 的已知限制，因此出现时不要把它算作新回归，也不要把 F-007 标记为完成。

## 3. 更适合读测试/接口验收的功能

F-003、F-004、F-005 需要真实生活线经历跨日积累，明早临时聊天无法完整验证。先读下列可执行规则：

- F-003：`tests/test_life_threads_v1.py`
  - 推荐只进入候选；日程不等于完成；覆盖时段不推进；重复结算保持幂等。
- F-004：`tests/test_sharing_reserve.py`
  - 只有真实经历能成为分享候选；频率、安静时段和未回应抑制生效；分享失败不假装成功。
- F-005：`tests/test_preference_evolution.py`
  - 同一体验只记一次；可信情境只来自真实 settlement；reset 不被旧体验复活；关闭后运行时不暴露偏好。
- F-008：`tests/test_comfyui_integration.py`
  - 当前只验收连接协议、状态、超时、取消和安全路径；角色自动发图尚未实现。

## 4. 建议验收顺序

1. 先用 10～15 分钟手测 F-001、F-002、F-006 和 F-007。
2. 再读 F-003～F-005 的测试名称与关键断言，确认产品规则符合预期。
3. ComfyUI 本机准备好后，单独做 F-008 真实连接验收；不要与角色自动发图混为一项。
4. 只有负责人确认自然表现后，才把对应功能从“待验收”改为“已完成”。

## 5. 串联测试覆盖什么

`tests/test_character_life_chain_integration.py` 使用同一个内存角色和同一份数据依次验证：

1. F-002 从世界锚点和日程解析“当前在家看剧”；
2. F-003 只在真实时段结束后推进生活线，并保存可信地点、室内外、活动类型和时段；
3. F-004 从已确认进展与体验生成分享候选；
4. F-005 从同一真实体验形成一次具体对象偏好；
5. F-006 通过独立事件账本改变状态，但亲密度保持冻结；
6. F-001 在三小时后把场景标为需要重新判断；
7. F-007 把可信运行态与偏好结论转成本轮回复动作，再交给 Persona 用角色口吻表达。

F-008 没有串进这条链，因为当前产品边界只是独立连接器。等角色自动发图的触发、许可、冷却和成本规则确认后，再新增 `F-004/F-007 → F-008` 的端到端测试。

## 6. Persona 与回复方式：明早待确认方向

### 现有 Persona 是否要更新

现有 Persona schema 已经能表达身份、性格核心、说话方式、关系边界、示例口吻、禁区和固定偏好，不需要为了 F-001～F-008 整体推倒重做。

后续需要的是社交卡的定向扩展，而不是把所有动态信息塞回 Persona：

- 为 DailyAgent 提供明确的生活习惯、活动倾向和可尝试项目种子；
- 为 F-003 提供显式结构化生活线 preset，不从自由 `lore` 猜作品；
- 补全不同角色的实际 Persona 内容和高质量对话示例；
- 世界锚点、实时状态、具体体验偏好继续分别存放，禁止自动回写核心 Persona。

### “直接代入角色”还是“先分析怎么回复”

推荐采用混合结构：

1. 最终生成模型始终直接代入角色，以第一人称自然回复；
2. 生成前由程序生成一张很短的内部判定卡，只给出可信事实、当前用户需求、主回复动作和禁止事项；
3. Persona 负责“怎么说”，判定卡负责“这一轮应该做什么”；
4. 不要求模型输出长篇分析或思维过程，也暂不增加第二次 LLM 调用。

这正是当前 F-007 的基础方向，但还没有完成更深的共情推断、用户可能回应预测和 F-009 心理假设。后续若要增加，可以先做受限的结构化规划器，再决定是否值得拆成第二个模型，而不是一开始就改成重型多 Agent。
