# F-002 · 社交世界锚点与日常代理运行时

| 项目 | 内容 |
|---|---|
| 状态 | Stage 2A 已实现 · Reviewer Round 4 PASS · 待负责人真机验收 |
| 适用范围 | 仅社交卡 |
| 优先级 | 高 |
| 前置依赖 | F-001 时间一致性 |
| 设计背景 | `docs/design/dailyagent-plan.md` |

## 1. 产品目标

让社交角色拥有连续、可解释且随真实时间推进的一天：她知道自己身处哪里、当地是什么时间和天气、当前在做什么、活动何时结束以及接下来准备做什么。

这是角色世界状态系统，不是 AI 业界所说的学习式世界模型。它不模拟整个物理世界，只维护与角色生活和对话相关、可验证的最小状态。

## 2. 卡片边界

- 仅卡片类型字段为社交卡时参与日常代理调度。
- 助手卡不生成私人生活日程，不虚构住处、娱乐活动或角色天气。
- 用户所在地与角色所在地完全分离；不得默认读取或推断用户位置。

## 3. 世界锚点

每个社交角色拥有稳定配置：

- 常驻城市；
- 角色时区；
- 世界模式：真实城市或虚构世界；
- 私人生活场景标签，如“自己的公寓”，不要求真实精确地址；
- 天气模式：第一版使用真实天气或关闭；不提供模拟天气。

默认推荐“真实城市 + 虚构私人空间”：城市、时区和天气可验证，住所、咖啡店等生活空间保持创作自由。

## 4. 日程与运行时

### 4.1 日程块

日程块至少支持：

- 开始/结束时间；
- 具体活动；
- 活动类型；
- 粗粒度地点与室内/室外属性；
- 可选伴随活动（例如学习时听歌）；
- 可选的持续生活线引用；
- 计划来源和版本。

日程只记录有依据的主要生活段落，不要求覆盖全天。时段之间允许自然空档；
空档表示“没有固定安排”，不由模型为了填满时间而编造活动。午睡、散步、
吃饭和无产出休息都是正常活动，微小动作不得被机械拉长为独立的一小时任务。

### 4.2 每轮运行时语境

聊天时提供：

- 角色当地时间；
- 当前城市与场景；
- 当前活动及开始/结束时间；
- 已经过和预计剩余时间；
- 下一项活动；
- 天气快照的来源与更新时间。

### 4.3 活动所有权

- 今日计划是基础活动真源。
- 临时事件作为带有效区间的覆盖，不直接与定时推进器抢写同一个活动字段。
- 临时覆盖结束后恢复基础计划，或触发重排剩余日程。
- 已经发生的日程不得因重新规划而被重写。

### 4.4 天气真实性

- 真实天气必须来自可追溯数据源并记录更新时间。
- 获取失败或数据过期时省略具体天气，不允许模型临时编造气温或降雨。
- 第一版虚构世界不接天气；不得用模拟数据冒充现实天气。

真实天气第一版采用 Open-Meteo：城市首次解析为经纬度，天气以 30–60 分钟快照缓存。每次获取当前天气与今日最高/最低温、主要天气、最大降雨概率；必要时保留少量小时预报。API 请求本身不消耗 LLM tokens，进入 prompt 的内容压缩为一条短语境。

### 4.5 旅行

- 旅行是带开始/结束时间的城市与时区覆盖。
- 旅行结束后自动恢复常驻城市。
- 地点转换必须留出合理移动时间。

### 4.6 V2 场景化日程模块（设计保留）

- Persona 中的旅行偏好和触发条件只产生候选倾向，不能直接生成已经发生或即将发生的旅行。
- 旅行只有在目的地、时间等必要事实成为已确认的 life thread 或结构化事件后，才能进入日程。
- 继续使用同一个 DailyAgent；基础日程 Prompt 保持通用，旅行日按需附加旅行场景模块，不新增独立 Agent。
- 展览、生日、约定、交付日及其他特殊事件后续采用同类的按需场景模块；普通日不加载这些内容。

## 5. 有限响应与重排

第一阶段仅在明确事件发生时调整日程：用户邀请、日历变化、角色明确改变计划、活动被临时事件打断。普通聊天不重新生成整天日程；必要时只重排“现在之后”。

## 6. 暂不进入本阶段

- 30–60 分钟一次的后台 LLM 心跳；
- 心情、精力、状态衰减和转移组成的完整角色状态机；
- 日终 reflection；
- 多角色同时调度；
- ComfyUI 图片生成；
- 偏好自动演化。

角色状态机强化属于独立功能 F-006，本需求文档不代表其规则已经讨论或定稿。

## 7. 验收标准

- 社交卡会按角色时区生成并推进日程，助手卡被可靠跳过。
- 活动边界、跨午夜、临时覆盖和恢复均有自动测试。
- 模型能够说清当前活动、剩余时间和下一项活动，但不会机械报时。
- 角色活动必须按真实可行耗时推进；“准备吃饭”等合理活动意图不能在两分钟后无依据跳成“已经做完并吃完”。
- 天气失败时不生成伪实时事实。
- 应用重启后可恢复当日运行时状态，不重复或倒退已经发生的活动。
- 用户画像、普通聊天摘要、用户工作和项目不会进入角色私人日程。
- 允许日程空档、午睡和伴随活动；重叠、乱序及明显不合理的长时微活动会被拒绝。

## 8. 当前完成度

### 已定稿的产品方向

- 仅社交卡拥有日常代理和角色生活；
- 角色拥有独立于用户的世界锚点；
- 默认采用真实城市与天气、虚构私人生活空间；
- 每轮需要知道当前地点、活动时间边界与下一项活动；
- 基础计划与临时覆盖必须分开，天气失败时不得编造事实。
- 日程不设固定块数，不强制覆盖24小时，允许自然空档与伴随活动；
- 用户生活和角色生活严格隔离，只有未来显式结构化共同约定可以形成共同活动。
- 当天首次启动或后端中断后恢复时，补建角色当地今日已结束日程的活动精细化；该结果必须标记为“追溯补建 · 计划细化”，只表达计划结构，不得冒充真实观察、实际完成或持续项目进度。

### 仍需继续讨论

- 弹性活动采用明确时间还是时间窗，以及何时允许变化；
- 临时事件结束后恢复原计划还是重排剩余日程；
- 旅行、通勤和地点移动的详细规则；
- 多角色如何分别调度与控制调用成本；
- 日程生成失败、连续失败和跨日切换时的产品表现。

### 已确认完成

- 仅社交卡进入 DailyAgent，助手卡不暴露社交卡私人活动；
- 每角色独立世界锚点、时区、常驻城市与私人场景；
- 每日计划生成、缺计划补生成和单飞/失败冷却；
- 当前活动、起止时间、已过/剩余时间、地点、室内外与下一活动进入运行时；
- 基础计划与临时覆盖分离，覆盖结束后恢复基础计划；
- 真实天气接入，缺少有效坐标或天气过期时明确省略而不编造；
- 世界锚点知名城市选择、真实天气开关和显式生成今日日程的前端入口；
- 角色日程不再读取用户画像、普通聊天摘要或用户日历；
- 日程允许空档和 `background_activity`，并校验排序、重叠及基础时长边界；
- 跨午夜、时区、DST、应用重启恢复与助手卡隔离自动测试。
- 当天历史日程按角色当地日期幂等补建精细化；未来活动仍只在 T-5 按需预热，自然空档不创建实体。

### 尚未完成

- 任意突发事件后的自适应剩余日程重排；第一版仅在覆盖结束后恢复基础计划；
- 旅行、通勤和地点移动的细粒度规则；
- 多角色同时启用后的调用预算、错峰和优先级策略；
- 任意城市搜索、旅行覆盖和更完整的日程编辑界面；当前前端仅提供知名城市预设与生成入口。

## 9. 第一版实施阶段

### 阶段一：社交卡边界与世界锚点

- 仅社交卡进入日常代理；
- 为角色提供常驻城市、时区、世界模式和天气模式；
- 用户位置与角色位置严格分离；
- 世界锚点缺失时使用明确的无世界信息降级，不临时编造。

### 阶段二：日程数据与运行时

- 日程块增加活动类型、粗粒度地点和室内/室外属性；
- 运行时计算当前活动、起止时间、已经过时间、剩余时间和下一项活动；
- 当前运行时作为结构化数据进入提示词，不要求角色机械复述。

### 阶段三：基础计划与临时覆盖

- 今日计划作为基础活动真源；
- 临时事件带开始时间、预计结束时间、来源和状态；
- 临时事件结束后恢复基础计划，只有明确无法恢复时才进入后续重排；
- 已发生的日程不得被重排覆盖。

### 阶段四：真实性与恢复

- 天气只使用带来源和更新时间的真实快照；
- 应用重启时依据已保存日程和当前时间恢复运行时；
- 恢复只计算当前应该处于哪个日程块，不在第一版自动宣称离线期间完成了书籍、剧集或创作进度；
- 生成失败时保留上一份可用数据或进入明确的无计划状态，不伪造成功。

## 10. 第一版完成边界

完成后，角色能够稳定知道自己当地的时间、地点、天气、当前活动和下一项活动，并正确处理带期限的临时事件。

以下内容不属于本功能第一版：完整状态机、持续生活线进度、分享储备、偏好成长、后台自主思考和 ComfyUI。

## 11. 负责人真机验收发现

### 2026-07-24 · 活动意图合理，但推进速度失败

- 历史反例：[Conversation C-004 / Segment B-C](PROMPT-MODEL-EVALUATION-LOG.md)；固定 Qwen 3.7 Max 后的正式复测记录进入[功能对话验收日志](FEATURE-CONVERSATION-ACCEPTANCE-LOG.md)。
- 11:53 接近中午，角色说“我也准备去吃饭了”符合时间和日常语境，判定为合理活动意图。
- 11:55 用户追问时，角色却称“刚吃完，自己下了碗面”。两分钟不足以完成准备、烹饪和吃完，判定为活动耗时连续性失败。
- 本例跨越两个 Provider Segment，不能归因成单一模型质量问题；但产品层必须保证可信角色活动不会因 Provider 切换或模型临场发挥而发生不可能的时间跳变。
- F-002 继续保持“待负责人真机验收”，不能因自动测试通过改为已完成。

后续专项复测固定一个模型、一个 Provider 和一个新 conversation，只测试“准备吃饭 → 两分钟后”的活动推进。允许“刚开始做、正在煮、还没决定、在等外卖”；也允许角色自然开玩笑，例如“两分钟怎么可能吃完，我才刚开始做”。不允许为了显得有生活感而宣称已经做完并吃完。

### 2026-07-30 · 活动事件按需精细化（已实现，待负责人对话验收）

- DailyAgent 仍只生成粗日程；`sleep/rest/leisure/meal/routine/social/focus/commute/other` 是九个一级分类，不限制具体活动数量。
- 每个粗事件采用 `activity_type → activity_kind → variant → 受控 detail → phase plan`。`detail` 只能逐字选择服务端模板中的安全描述，不能生成菜名、人名、地点、作品名、绝对时间或完成宣称。所有类别共享 `planned/preparing/active|waiting/wrapping_up/completed` 协议，阶段和完成资格只按服务端保存的真实时间边界计算。
- `daily_activity_ticker` 在下一事件开始前五分钟内幂等预热；应用关闭或错过窗口时，ticker 或社交卡首次运行时会为当前事件补算。
- 精细化可进行一次普通 LLM JSON 请求，让当前激活 Provider 只从服务端白名单选择配对的 `kind/variant/detail`；不使用 Function Calling 或 Skill。非法 JSON、调用失败均直接保存带安全 detail 的保守 fallback，不重试、不阻塞日程或聊天。
- 一次活动实例按角色及精确 `slot_id + plan_version + source_version` 全局持久化，跨 Conversation 和应用重启复用；计划或 slot 变化不会误用旧实例。
- 主聊天只接收紧凑的“角色当前活动实例”块，包括当前 phase、阶段耗时、允许下一阶段和完成限制；模型不得写绝对时间、直接设置 phase，或重新开启 legacy `<state_update activity>`。
- `visual_scene_snapshot_json` 仅作为未来 anime/ComfyUI 场景结构预留；本轮不生成图片、不提交 ComfyUI 任务，也不保存用户数据。
- 自动测试只证明结构、幂等、降级与时间推进规则成立；F-002 继续保持待负责人真机验收，C-005/C-006/C-007 仍需固定 `Qwen 3.7 Max · 国产线路` 独立执行。
