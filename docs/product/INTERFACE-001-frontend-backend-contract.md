# INTERFACE-001 · 前后端交互契约草案

日期：2026-11-22 复核。状态：需求级接口草案，未实现、未锁定路由或传输格式。对应 [PRD v0.95](PRD-momo-next.md)；先用麦麦原版网页与官方桌宠验证，再按实际缺口映射已有接口，正式视觉设计后置。下文的字段与多会话支持是设计建议，不表示产品已确认多段会话，也不要求重建整套后端或自研每个端点。

## 1. 所有二级功能的填写要求

每项同时记录：用户/前端输入、后端结果、过程事件、错误/取消、用户可操作的控件、状态归属与配置生效时机。下面的字段和事件名为建议，详细设计可修改。前端仅需能验证行为，不按此提前设计正式页面。

公共关联信息建议包含 request_id、session_id、character_id；涉及任务/模型回复时再关联 run_id、response_id。前端发起请求后，后端回传对应请求及实际状态。支持同一角色多会话和后续多角色，不使用一个全局“当前回答”承接所有音频。

### 1.1 设置交互分类

用户确认至少区分能力启停与模式/实现选择，见 PRD §5.10.1。建议请求将 `enabled` 与 `selection` 分开表达；选择中按实际能力提供 mode、provider/model 或角色 voice_config 引用，不强制每项都有全部字段。特定 Skill/MCP 按独立标识启停，语音能力可以同时具有开关和多项选择。

返回区分已保存配置、当前实际生效配置、运行就绪/错误状态以及生效时机。建议停用保留选择，删除为独立操作；模型切换失败不应伪装为已生效。不支持的引擎/声音/模式组合提供明确原因。请求字段、作用域与运行中切换行为继续按功能细化，未实现接口。

**实现来源约定（2026-11-18）：**下列契约描述 Momo 需要交换的信息与控制，不要求重写现成插件的内部机制。优先映射插件已有接口和事件，必要时做最小适配；仅对实际缺口新增能力。语音候选覆盖与待验证项见 PRD §5.4.8。

**主机与客户端（2026-11-20）。** 后端优先部署在用户的 RTX 5070 Ti 主机，Mac、手机等终端连接它。语音与摄像头取自发起通话的设备并在该端播放。主屏和游戏状态取自本次要观察的设备，接回控制的请求要到达实际执行桌面操作的设备。实现时按同一次会话验证往返。

**计划交接（2026-11-22）。** 用户确认先验证出差前将服务端交给 Mac、返程交回主机，见 [PRD §5.12](SPEC-momo-next-details.md#512-主机与-mac-的计划交接2026-11-22-已确认验证方向)。验证时报告当前运行端、交接结果和实际可用能力；先使用已有导出/恢复与连接配置入口，尚未定义新端点或自动切换协议。

## 2. 语音输入、输出与控制

**TTS 能力与已有资产（2026-11-18）：**承接用户自行微调的 GPT-SoVITS 模型，角色声音配置可引用其模型组合与参考音频；具体字段及兼容版本接入时核对。声音表达能力按实际引擎与模型返回，不预设情绪参数、情绪标签或句内控制已受支持。参考音频引导与显式情绪控制应区分，见 PRD §5.4.6 / INV-33 §12。

| 交互 | 前端/客户端提供 | 后端返回或发出 | 测试前端需要表现 |
| --- | --- | --- | --- |
| 管理 TTS 库 | 引擎/服务引用、模型/音色配置、适用的权重组合与参考素材/文字/标签 | 库列表、详情、保存/启停/移除结果及可用状态 | 管理可选声音；素材接入方式后定 |
| 绑定角色与试听 | 角色、声音配置引用、试听文字及引擎支持的选项 | 绑定结果、实际生效配置；试听音频与播放/停止状态 | 选择声音、试听与停止，沿用旧版管理思路 |
| 查询引擎能力 | 模块种类，必要时 provider_id | 可用模型/语言/音色、流式/取消能力、就绪状态、实际限制 | 选择列表、不可用原因；不提供引擎不支持的参数 |
| 保存语音配置 | ASR/TTS 或实时音频适配器配置引用、模式、说话人区分开关 | 保存结果、实际生效配置、立即/下次会话/重启生效说明 | 区分“保存了”和“已生效” |
| 开始语音会话 | 会话/角色、duplex_mode、interrupt_policy、speaker_detection_enabled、音频格式协商信息 | 会话确认、支持/拒绝原因、实际采用的格式与配置 | 正在连接/可收听/失败，展示实际模式 |

| 返回回复和声音 | 角色音色引用；文字由回复或测试输入产生 | response_id、segment_id、音频流/引用及格式、可用的文本关联、结束/失败事件 | 按序播放；字幕和角色状态可关联 |
| 前端播放回报 | response_id、segment_id、played_ms、playing/paused/stopped/completed | 后端更新已播放状态及中断点；确认接收 | 将“合成完成”和“播放完成”分别显示 |
| 打断当前说话（无独立停止按钮要求） | 指定目标 response_id 和停止范围 | 当前输出已取消/已结束/无法撤回等真实状态 | 本地立即停止对应播放并清理缓冲，忽略该旧回复迟到音频 |
| 暂停/恢复 TTS | TTS 输出启停状态 | 实际输出状态与生效结果；暂停当前播放沿用打断控制 | 暂停时不发声、仍可显示文字；不自动关闭麦克风或 ASR |
| 退出语音/结束会话 | 既有语音模式退出或 session_end 动作 | 收听/会话状态确认与资源处理结果 | 麦克风使用状态清楚；不另设暂停收听控件，结束不自动取消无关后台任务 |
| 引擎/设备错误 | 客户端上报采集/播放错误；后端上报推理/连接错误 | 模块、错误码、可重试信息、受影响会话/回复 | 展示原因及对应操作，不能假报已发声 |

输入和输出使用用户端系统当前默认设备，不要求 Momo 提供设备列表或选择面板；自身回声处理优先复用插件/运行环境能力，验证避免自触发且能接住用户插话。后端持有模型/适配器配置；角色持有音色映射；客户端持有播放缓冲与实际进度。凭据用服务端配置引用传递，设置读取不回传明文密钥。

**按场景打断（2026-11-18 确认方向）：**直接对话时用户开口先让话；后台陪伴时结合呼叫、指令及上下文判定是否对 Momo 说话，见 PRD §5.4.7。契约预留交互场景、让话/打断结果及被中断内容关联，沿用 response_id、segment_id 和真实播放进度支持明确“继续”。恢复粒度与自动续播规则后定；取消语音回复不等于取消无关后台任务。

### 2.3 激活后的持续收听与自动分段

用户要求承接旧 Momo 的“唤醒＋持续监控语音”。逻辑契约预留：客户端发起激活、暂停或结束，返回实际收听状态或失败原因；每次发言开始/结束关联 utterance_id，分段后自动提交 ASR 并将最终文本关联会话记录和回复，收听会话继续等待下一段。收听状态与单次识别/回复状态分别维护。

具体激活来源（当前源码为按钮；唤醒词入口未定位）、空闲超时和配置生效方式后定；沿用既有字段关联，不要求前端每句话再点击发送。暂停或结束收听对正在处理回复的影响归对应控制策略定义，不预设取消后台任务。

#### 唤醒插件契约（2026-11-18 方向已确认，字段为草案）

唤醒作为独立插件，向语音会话控制提供激活信号；正文转写继续由 ASR 模块承担。宿主负责插件注册、启停与资源释放；不要求另起进程，DSH 包装和部署位置后定。

| 契约 | 输入 / 控制 | 输出 / 状态 |
| --- | --- | --- |
| 能力与配置 | 查询能力、设置检测参数；关键词检测实现可提供唤醒词配置 | 支持的参数、当前生效值、变更是否需重启 |
| 生命周期 | 启用、开始检测、暂停、停止及卸载 | 实际状态：关闭、准备中、检测中、暂停、错误；失败原因 |

### 2.4 特定场景免唤醒记录与主动陪伴（方向已确认，接口草案）

用户确认游戏、干活等场景中免唤醒记录，并希望 Momo 主动吐槽、鼓励或接话。接口应分别表达“是否采集/识别/记录”和“是否触发回复”，保留原有唤醒插件及普通语音交流路径。字段、具体参与策略和场景启用方式尚未确认。

- 读屏范围（已确认）：开启后使用当前设备的系统主屏。前台应用切换时沿用当前读屏状态与画面来源。
- 场景控制：进入、暂停、退出；关联 scene_id、会话及选定音频来源；返回实际收听/记录状态与失败原因。
- 记录事件：沿用 utterance_id 与 partial/final，补充场景、时间、来源和记录关联；可区分场景记录与直接对话，不将每条记录自动送入回复流程。
- 场景线索：传递场景、发生时间、来源及可追溯记录引用，描述游戏结果/工作进展等观察或推断；具体事件种类后定，不能由 ASR 文本缺失推定游戏胜负。
- 回应策略：支持场景主动参与方向，预留参与程度、临时安静和恢复控制；仅记录、呼叫才回应作为可选策略待定，不指定默认值。
- 主动发言：关联场景和触发依据，沿用正常回复的文本、音频、消息记录及取消链路；可表达待发/已发/取消，避免场景退出后仍播放已过时评论。具体触发、去重、延后规则后定。
- 退出边界：报告停止采集与记录的实际状态；退出前已采集片段的收尾和保留规则后定，迟到结果不得串入其他场景。

麦克风、系统/队友音频接入范围与原始音频保存尚未确定；场景记录不自动等于长期记忆。本文不承诺具体采集实现。

2026-11-18 感知复用调研补充：场景线索可由音频转写、应用状态、截图/短时间线或游戏事件适配器提供。建议保留来源、捕获时间、场景/会话、观察内容及证据引用；视觉推断与原始事件分别表达，旧帧或退出前未完成的分析按场景状态处理。采集更新不要求逐条触发模型回复。实现参考见 INV-36，未锁定供应方字段或插件协议。

### 2.5 外源事件筛选与择时提醒（需求契约草案）

用户确认各类外源消息到达后统一考虑处理策略，邮件是其中一个来源；输入可经现成 MCP、DSH 插件等接入，具体协议后定。

逻辑上保留事件标识、来源、时间、内容或引用，以及适用的账号/会话/场景关联。筛选结论与通知状态分别表达：是否值得提醒、暂缓原因、是否已汇总/已通知及原消息关联。字段是建议，不要求新增复杂事件框架或重写已有插件。

响应复用已有记录、语音和角色输出。查询与新消息发现分别核对；只收到摘要时按实际内容判断，必要时另读原文。其他优先级、保留与自动外发规则后定。当前不开始接入或实现。

## 3. 全双工状态与打断建议

duplex_mode 与 interrupt_policy 分开：全双工保持输入/输出可同时工作；是否让话由策略判定。候选策略为自动判断、用户手动控制、听完当前段再回应，最终选项和默认值待确认。示例：短应答“嗯”可继续播放；明确要求停下或真正接管话轮则停止旧输出；误判后是否续播另定。短应答判断不能只用固定关键词。

收听状态、生成状态、播放状态、后台任务状态分别表达，不能用一个互斥枚举让 speaking 必然关闭 listening。建议事件包括 input_speech_started、transcript_partial/final、response_text_delta、audio_segment、playback_stop、response_cancelled、session_state、error；仅暴露适配器确实支持的事件。

停止当前回复需要处理播放器、队列、TTS 请求和必要的模型生成；不能只让页面静音而旧内容继续排队。任务取消用独立目标/动作。实际听到的内容以播放回报为依据；精确到字的对齐需要额外时间戳能力，不由 played_ms 虚构。

配置作用域（全局默认/角色/会话）及覆盖顺序待详细设计；返回生效值。声纹关闭不阻止匿名语音输入；默认是否开启尚未确定。模块关闭应停止对应处理，独占资源是否卸载或保温按资源策略明确，不承诺瞬间释放全部内存。

## 4. 语音模块边界建议

- ASR 适配器：音频→识别事件/文本，声明批量/流式支持。
- TTS 适配器：文本及实际可用音色→音频，声明格式、流式粒度、取消与参数支持。
- 回合控制：语音活动/说完判断、短应答与真正打断、输出队列协调。
- 可选说话人模块：分离不同说话人或识别已注册身份，按已选范围实现。
- 客户端音频：采集、播放、设备、回声处理和实际播放回报；部署位置在架构阶段落实。
- 若采用原生实时音频模型，通过能力声明接入；不伪装为可任意混搭的独立 ASR/TTS。Momo 的角色/任务仍由自身应用管理。

设置中允许选择已接入的引擎、模型、服务位置、角色音色和相关控制。具体高级参数以引擎能力为准。模块化不要求每项单独启动常驻进程。

## 5. 验证情境草案

1. 全双工中外放回复且接收用户语音；“嗯”与明确打断分别观察处理结果，记录误判。
2. 取消回复 A 后，迟到的 A 音频不再播放，回复 B 正常播放；后台任务状态不被误改。
3. 说话人区分属于后续可选模块：一期不加载仍可完成基础语音交流；后续实现时再验证关→开→关、基础 ASR 可用及状态/配置/资源变化。
4. 换一个 ASR/TTS 适配器，能力目录与配置表反映实际差异；不支持的模式明确反馈。
5. 测试前端回报实际播放结束，后端不能在仅完成合成时宣告用户已听完。
6. 在 Momo 客户端使用 ASR 交流后，可回看识别文本与对应回复；若展示增量转写，同一次发言更新为最终文本且不重复新增消息。

当前仅建立接口需求，无端点已实现或验收通过的声明。来源与 AnifLive-TTS 候选见 [INV-33 §8](../INV-33-legacy-capabilities-and-technology-refresh.md)。

## 6. 长期记忆管理

聊天接受用户的自然语言纠正。设置入口读取有效记忆条目，用条目标识提交修改或删除；操作成功后显示实际保存结果，失败时保留可见错误。两种入口的更改都应影响之后的查阅与召回。接口路径与条目类型映射在接入现有记忆服务时确定。见 [PRD §3.4](SPEC-momo-next-details.md#34-首轮记忆纠正与管理已确认)。
