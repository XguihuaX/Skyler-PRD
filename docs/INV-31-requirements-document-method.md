# INV-31：Momo 需求文档写法与现有 PRD 差距

核对日期：2026-11-17。性质：方法调研与建议；不新增已确认产品功能。

## 1. 结论

当前 `product/PRD-momo-next.md` 是整体产品需求的工作草案，已包含定位、功能域、范围决策及填写模板，尚未形成完整的开发与验收依据。保留该主入口，按功能逐步补齐。单角色人设应先定义产品需要提供的能力和行为，再填写某个角色的具体内容，随后选择 Prompt、模型和运行机制。

对话是需求获取的一种方式。需要改进的是对话后的整理、确认、版本和验收关联，而不是要求全部需求一开始就固定。

## 2. 核对的资料及适用范围

| 来源 | 调研得到的方法 | 在 Momo 中的用途 |
| --- | --- | --- |
| [Atlassian PRD 实践](https://www.atlassian.com/agile/product-management/requirements) | 用目标、背景、假设、用户故事和范围等建立共同理解；持续更新，避免开工前把全项目所有细节固化 | 产品主文档保持清楚、可迭代；详细程度随阶段增加 |
| [IEEE：ISO/IEC/IEEE 29148-2018 官方概述](https://standards.ieee.org/ieee/29148/6937/) | 需求工程包含需求质量、属性以及贯穿生命周期的迭代过程 | 区分需求获取、分析、规格与管理；本轮仅核对公开概述，不声称全文合规 |
| [NASA 手册附录 C](https://www.nasa.gov/reference/system-engineering-handbook-appendix/) | 单条要求清晰、单一、有依据、可验证；描述需要满足的结果，避免无依据地规定实现 | 检查具体条目是否可开发、可验收；不引入航天项目审批流程 |
| [SEBoK：System Requirements Definition](https://sebokwiki.org/wiki/System_Requirements_Definition) | 从用户需要推导系统要求；关联来源、设计及验证；管理未定项和变更影响 | 将用户场景、需求条目与验收对应，保留依赖和待解决问题 |
| [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) | 用任务、重复试验、评分、执行记录与实际结果评估智能体；结合自动检查和人工判断 | 人格、自然聊天、记忆等需要情境评估；单次好回复不作为整体效果证明 |

以下结构是针对 Momo 的裁剪建议，不是上述资料共同规定的一套强制目录。

## 3. 整体需求应覆盖什么

| 部分 | 要回答的问题 | 现有文档情况 |
| --- | --- | --- |
| 产品目标与成功标准 | 为谁解决什么问题，什么结果说明值得使用 | 有定位，实际痛点和成功标准待补 |
| 使用环境与产品边界 | 本机、外部服务、用户分别负责什么，有哪些已知约束 | 有部署顺序，系统边界和外部依赖待补 |
| 版本范围与功能地图 | 本阶段做什么，后续做什么，各功能如何关联 | 有八个功能域和部分范围决定，首版范围未完成 |
| 核心用户场景 | 从用户提出需要到获得结果，完整过程是什么 | 有示例，完整流程及异常情境待补 |
| 功能需求 | 在什么条件下接收什么输入，产生什么行为和结果 | 有模板，人设等具体条目待讨论 |
| 数据与外部交互 | 保存什么、谁可修改、什么时候失效；与文件、邮件等如何交互 | 有记忆方向，具体规则待补 |
| 质量要求 | RAM、响应时间、Token、可靠性、可用性应达到什么程度 | 已列关注方向，条件、指标及目标待确定 |
| 验收与变更 | 每项要求怎样证明满足，改变后影响哪些场景与实现 | 有状态区分，逐条验收、依赖及变更记录待补 |

无需现在填满全部内容。优先建立整体边界和功能地图，再让当前选定功能达到可讨论、可确认的详细程度。

## 4. 单项功能的建议记录格式

```text
编号 / 名称：沿用所属 N-xx 功能域，细项获得稳定编号
状态 / 优先级 / 所属版本：需求确认状态与实施状态分开
用户需要与来源：谁在什么情境下需要什么，为什么
范围：包含什么、明确后置什么
前提和触发：从哪里进入，需要哪些输入或已有状态
正常流程：系统行为、用户决定、可见结果
异常流程：与该功能相关的失败、更正、中断、取消或恢复
数据和依赖：持久信息、外部服务、其他功能、相关用户控制
质量要求：适用条件、测量方式、目标；未知值及解决方法
验收：具体情境、预期结果、检查方法
待决与变更：问题、影响、确认日期；替换旧决定的原因
```

简单功能按需缩短；不为每项机械填入无关的取消、重启或权限流程。若已确认的技术、平台或接口属于真实约束，应明确记录。架构、Prompt 和具体算法另在设计中关联需求。

## 5. 人设需要区分的三个层次

| 层次 | 例子 | 当前如何处理 |
| --- | --- | --- |
| 产品能力与行为 | 是否支持用户定义人格；哪些可编辑；闲聊和办事如何保持身份连续；修改如何生效 | 先讨论，选中后写成需求 |
| 具体角色内容 | 名字、经历、性格、称呼、对话样例 | 作为该功能的内容配置与验收素材，随后填写 |
| 技术实现 | System Prompt 结构、Planner/Replyer、样例检索、模型选择 | 对应需求选型，尚未确定 |

上一轮先问“沿用已有角色还是原创 Momo”过早转入内容配置。本轮调整讨论顺序，不删除已有范围决定。

示例（仅示范写法，未获用户确认）：

- 用户需要：我希望可以调整 Momo 对我的称呼。
- 功能条目：用户保存新的称呼设置后，系统应在后续新生成回复的称呼位置采用该设置。
- 待决：当前生成中的回复是否受影响；历史消息是否保持原样；失败时如何提示。
- 验收素材：将称呼从 A 改为 B，在适合出现称呼的情境中检查后续生成结果；测试修改失败和重新打开后的设置状态。

“自然、有个性”等体验目标还应提供允许的表达差异和不合格示例，由真实使用评价配合重复情境测试；不规定逐字匹配，也不预设未经讨论的通过率。

## 6. 支持逐项讨论的工作方式

1. 从整体功能地图选当前项；每轮只问一个会影响功能范围或行为的问题。
2. 用户回答后提炼成需求草案，解释实际含义和仍未决定的部分。
3. 明确决定直接记录；示例、建议及歧义继续保留为讨论中。
4. 本项逐步补齐相关流程、质量与验收，检查与已确认功能有无冲突。
5. 进入实现前确认本批次的需求版本和验收；后续新增想法先评估影响，再决定并入当前批次或后续版本。

整体 PRD 继续作为一个入口；条目长到不便阅读时再拆分详细规格，并保留链接。无需立即增加一套 BRD、MRD、SRS 和独立需求管理平台。
