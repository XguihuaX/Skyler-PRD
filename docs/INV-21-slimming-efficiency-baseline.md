# INV-21 · 代码瘦身效率基线

日期：2026-10-02。范围：REF-001 的效率切口。下列历史日志与合成基准不能直接当作当前真机的改后收益。

## 调查数据

- `logs/backend.log` 中可解析的 `_build_messages` 计时有 171 条：中位数 320 ms，P90 575 ms，P95 661 ms；最大值 15,225 ms 是历史长尾。2026-07-24 一轮 `_build_messages` 为 495 ms，其中 `search_relevant_memories` 的查询编码为 447.1 ms，说明向量编码可能主导该轮耗时；这不是当前版本的受控对照。
- `logs/token_probe.jsonl` 有 1,422 条可解析的工具 schema 记录，其中位数 9,423 Token。该日志跨多个项目版本，只能说明请求成本热点，不能证明当前固定工具集合大小。
- 当前本机直接导入时仅注册 5 个工具 schema（731 Token）；重复分词中位数约 0.22 ms。合成 60 个工具、8,041 Token 的同进程基准中，整次观测日志 `emit_sync` 中位数约 3.19 ms。重复 schema 分词真实存在，但本地 CPU 节省上限只有数毫秒，不宜优先引入缓存与失效状态。
- 当前本机数据库的 15 条 memory 都有 embedding。给“全是无向量旧条目”增加跳过编码分支，对这份数据没有实际收益。
- `get_summary` 是只读查询；本机对一个不存在的测试 key 连续读取，热态中位数约 0.30 ms。纠正类消息此前读完立即丢弃，当前切口省去这一次读取。该数字只代表查询本身，不代表端到端对话延迟改善。
- renderer 的画像、活动和记忆读取彼此独立。曾尝试并发读取：20/20/80 ms 合成延迟下，8 次配对中位数 126.57→83.28 ms，消息列表相同。但同一真实数据库副本的两轮配对分别为 389.1→389.0 ms（5 对）和 611.6→599.8 ms（8 对、波动较大），消息分别 5/5 与 8/8 完全相同。连续两轮未证明稳定实益，已撤回这处并发读取，保持串行装配。

## 行为约束

- `chat._build_messages` 对纠正类消息执行长期记忆检索后，不把检索结果注入提示词。看似可省一次向量编码，但 `search_relevant_memories` 还会更新召回条目的 `access_count` 与 `last_accessed_at`，影响遗忘曲线和以后排序。直接跳过会改变记忆语义，当前不做。
- 每轮全量工具 schema 的 Token 成本高；按任务筛选工具会改变模型可见能力，须独立质量对照。`ToolRegistry.list_schemas()` 本身只是返回已注册 schema 的列表，不能把 Token 成本归咎于这一步 CPU 工作。
