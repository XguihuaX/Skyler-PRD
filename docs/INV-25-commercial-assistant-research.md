## 1. 总体判断

Momo 已具备桌面界面、模型调用、工具、角色、记忆和语音的基础。当前主要差距是：尚未锁定用户每天真正愿意使用的核心场景，任务执行与错误恢复需要更明确的状态，资源和成本缺少当前版本的完整基线，配置迁移、备份与凭证保护仍需专项验证。对外安装、签名更新和发行资产授权是未来发布阶段的额外工作。

建议继续使用 React / Tauri / FastAPI / SQLite / LiteLLM 的现有骨架，逐步明确模块责任。已有技术栈足以支持可靠的个人助手；本次未发现必须全量迁移到某个 Agent 框架才能达成目标的证据。架构选择应由真实任务的持续时间、恢复要求和部署形态决定。Anthropic 对确定性工作流和模型自主执行的区分，是这一判断的参考。[工作流与 Agent](https://www.anthropic.com/engineering/building-effective-agents)

| 方向 | 商业产品要解决的问题 | 当前判断 | 首先需要取得的证据 |
| --- | --- | --- | --- |
| 1 日常实用性 | 用户为何持续打开、愿意交出什么工作 | 方向成立，具体首批场景未确定 | 真实任务访谈、现有做法耗时、一次完整任务的价值 |
| 3 RAM | 用户是否愿意让 Momo 长期开着 | 有模型预热和生命周期候选开销，尚无完整实测 | 进程归属清单、冷暖启动、空闲/语音/切角色/长时运行曲线 |
| 5 上下文等 | 是否记得对、选对工具、执行可恢复、成本可控 | 有基础，也有明确代码级缺口 | 记忆失败重放、检索与工具任务集、逐轮费用和延迟 |
| 2 MaiBot / Hermes | 如何形成自然表达和可积累的工作能力 | 应按机制选择性借鉴 | 角色体验盲评、技能复用成功率、额外成本、授权条件 |

四个方向需要协同：任务 1 决定优化什么；任务 3 和 5 决定能否长期可靠运行；任务 2 提供表达与复用机制。建议把“1 的需求发现 + 3/5 的基线”放在同一轮，把 2 的轻量人设试验穿插其中。完整全双工、大规模图记忆、自动自我改写和模型微调需有具体证据再投入。

## 2. 任务 1：从“有什么功能”转向“用户愿意交给 Momo 什么工作”

### 2.1 产品定位与参照

可验证的定位假设是：有稳定人格、能理解个人上下文、能跨日跟进事务的桌面助手。针对自用，需要证明它比用户当前做法节省时间、减少遗忘，以及角色和主动性是否让用户愿意长期保留它。

三个相邻参照说明商业体验的不同重点：

| 参照 | 官方材料可确认的机制 | 对 Momo 的启发（本报告判断） |
| --- | --- | --- |
| Raycast AI Extensions | 普通扩展可暴露工具，让 AI 调用其能力 | 保留直接操作入口；自然语言和按钮共用同一能力，降低失败后的接管成本 |
| Apple Shortcuts | 把应用动作编为可重复流程，并提供自动化触发 | 对步骤明确的任务复用确定性动作；LLM 负责理解和选择 |
| Notion Enterprise Search | 连接外部内容，查询遵守连接应用的用户权限；权限存在同步周期 | 搜索有来源，权限变更需要失效机制；已有连接器不代表实时授权永远正确 |

来源：[Raycast 工具设计](https://developers.raycast.com/ai/learn-core-concepts-of-ai-extensions)、[Apple 自动化](https://support.apple.com/en-qa/guide/shortcuts-mac/apdfbdbd7123/mac)、[Notion 权限与隐私](https://www.notion.com/help/enterprise-search-security-and-privacy-practices)。以上是产品机制参照，本轮没有做竞品上手性能比较，也没有验证市场规模。

### 2.2 需求发现必须是任务 1 的正式工作

先和用户做一轮场景访谈，再建议记录 7 天实际遇到的事情：何时想找 Momo、最后是否用上、哪里需要自己接管。单人连续使用记录就是当前最直接的价值证据。以后若转为对外产品，再另做同类目标用户访谈；多人市场研究不是本轮自用阶段的前置条件。

每次先问“最近一次是什么时候，怎么做的”，再讨论愿望。每轮只推进少量问题，复述理解后写成场景卡：

| 场景卡字段 | 应记录的内容 |
| --- | --- |
| 人与目标 | 谁，在什么情况下，要完成什么结果 |
| 当前做法 | 应用、手工步骤、每周频率、耗时、失败或遗忘代价 |
| 输入与来源 | 文件、账户、选中文本、窗口、用户口述；可读取范围 |
| Momo 的职责 | 仅整理、提出建议、准备草稿、确认后执行、限定条件自动执行 |
| 交互 | 文字/语音/通知；什么时候允许打扰；需要哪种角色表达 |
| 完成与失败 | 哪个外部记录证明成功；失败怎么继续、撤销或交回用户 |
| 价值证据 | 本次省时、用户修正量、是否主动复用、是否愿意继续授权 |
| 决策状态 | 用户原话、产品解释、待确认项、已选择/暂缓；不要混写 |

建议按“用户痛点与频率、现有替代方案、可验证结果、接入成本、误操作代价”讨论排序。没有访谈前，不给邮件等候选赋予看似精确的商业价值分数。

### 2.3 候选场景池，不等于首版范围

| 任务族 | 可能的真实请求 | 最小可验证交付 | 特别需要沟通的约束 |
| --- | --- | --- | --- |
| 信息整理 | “这些消息/网页/文件有哪些需要我处理？” | 带来源的摘要与候选事项 | 允许哪些来源，重要性怎么定义 |
| 时间与跟进 | “明天出门前提醒我，没处理就稍后再问” | 可查看/编辑/取消的结构化提醒 | 休眠、关机、时区、专注时段、重复通知 |
| 文档与文件 | “把这批材料整理好，找出需要补的部分” | 可审阅的分类方案、草稿或结果清单 | 文件范围、版本、覆盖与撤销 |
| 沟通准备 | “帮我写一份回复/会议准备材料” | 关联原材料的草稿 | 收件人、语气、附件、发送前确认 |
| 网页与电脑操作 | “在指定网站查找并填写这份信息” | 在限定应用完成步骤并核验结果 | 登录、验证码、界面变化、用户同时操作 |
| 日常陪伴与建议 | “我专注时别打扰，休息时帮我回顾今天” | 有依据且可关闭的提醒/交流 | 打扰容忍度、真实事件与角色设定分开 |
| 模型连接 | “选择更便宜或更擅长这项工作的模型” | 有能力说明、错误状态与费用信息的接入 | 账户、网络、费用、隐私和数据位置 |

### 2.4 执行路径：按可靠性选择接入方式

建议优先比较：官方 API / OS 接口 → 已审核的 MCP / 应用动作 → 浏览器结构化控制 → 桌面 AX 配合截图。选择依据是当前任务的稳定性、可验证性和维护成本，不要求所有场景都经过所有层。

“像 Codex 内部浏览器一样流畅”涉及持续会话、稳定目标定位、观察与动作的循环、工具响应时间、错误恢复和模型能力。只扩大权限无法保证这些指标。OpenAI 的 computer-use 文档也要求应用执行动作并把新截图回传给模型；模型并不自行拥有完整的执行环境。[Computer use](https://developers.openai.com/api/docs/guides/tools-computer-use)

Momo 的候选执行结构：

~~~mermaid
flowchart TD
    U["用户目标与任务范围"] --> T["任务状态与预算"]
    T --> C["组装相关上下文、选择工具"]
    C --> M["模型提出步骤或回答"]
    M --> P["代码检查权限、参数与确认状态"]
    P --> E["API / MCP / 浏览器 / 桌面执行"]
    E --> V["读取结果并核验"]
    V --> T
    V --> R["完成、部分完成、失败或交回用户"]
~~~

建议保存 task、step、attempt、external_result_id、approval、deadline、budget 等状态。先用现有 SQLite 支持单机任务，审计是否已有可复用表；不直接复制旧 retired todos。

对“请求发出后超时”的写操作，要进入结果未知状态并先查询外部记录。重复执行可能造成重复邮件、重复日程或文件覆盖，不能简单重试。应用崩溃后恢复需要带原操作标识，权限或确认条件变化后重新检查。目标是可恢复、可核验，而不是承诺跨所有外部系统的绝对 exactly-once。

对于提醒，分别记录“已排程、已提交给通知服务、通知服务已接受、用户已查看/确认”。没有回执时不能把“已提交”写成“用户已收到”。电脑关机时本地任务无法执行，必须明确采用系统计划通知、后台服务、云端投递还是恢复后补发；每条路径都需要真机验证。

### 2.5 邮箱只是展示商业接入成本的例子

如果访谈最终选中 Gmail，读取邮件的权限会涉及 restricted scopes；官方说明传输或在服务器保存相应数据会触发额外安全评估要求，需要按实际数据流核对。向云模型发送正文也必须纳入数据流分析，不能因“桌面应用”就假设豁免。[Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)

Gmail 的 watch 依赖 Pub/Sub 且需要续期；Microsoft Graph 的通知也依赖订阅生命周期。因此商业成本包括授权、增量同步、过期恢复、撤销、配额与支持，不只是一个摘要提示词。[Gmail push](https://developers.google.com/workspace/gmail/api/guides/push)、[Graph notifications](https://learn.microsoft.com/en-us/graph/change-notifications-overview)

模型接入建议延续 LiteLLM，并维护已验证能力表：流式输出、工具调用、结构化输出、视觉、音频、缓存、上下文限制、超时与错误类型。支持一个供应商不代表其每个模型都支持全部能力。LiteLLM 有路由与回退机制，但项目是否正确配置、何时可以切换仍需自行验证。[LiteLLM Router](https://docs.litellm.ai/docs/routing)

常规商业路线可评估 BYOK 或产品托管 API 额度。ChatGPT 与 API 的计费体系不同；官方订阅授权渠道如需接入，应独立核验当前参与条件，不把现有 ChatGPT 登录等同于 Momo 获得订阅额度、历史对话或记忆权限。[OpenAI 计费说明](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)

### 2.6 产品验证

首个闭环应来自访谈结果，范围先限定为一个主要来源、一个任务族和可明确核验的结果。以用户连续自用记录为主：

- 从启动到完成有用任务的时间，以及授权/配置中断的位置；换目录或重装后是否仍能恢复。
- 每周完成的有效任务数、净省时、需要人工修正的步骤、用户主动复用率。
- 用户拒绝建议、关闭主动性、取消权限或放弃使用的原因。
- 任务成功率按任务族和难度报告；用户主动取消单列，不能通过移除失败样本提高成功率。

“聊天轮数多”和“角色说话自然”可以是体验信号，但不能单独代表日常助手的产品价值。

## 3. 任务 3：把 RAM 变成可测量、可解释的产品预算

### 3.1 当前证据

- backend/main.py:358 同时安排 embedding 和 Whisper 预热。Whisper 类虽然按首次请求加载，但启动时主动调用其加载路径，所以产品仍产生启动预热。
- frontend/src/hooks/useLoadingSequence.ts:97 将 embedding、Whisper、WebSocket、Live2D 四路都作为 appReady 条件。改成按需加载必须同时设计真实的能力状态与就绪契约。
- backend/memory/long_term.py:37 导入 sentence-transformers，使用多语言 MiniLM；需要测模型权重、PyTorch/native runtime 与查询缓存各自占用。
- frontend/src/hooks/useAudio.ts:210、frontend/src/hooks/useWebSocket.ts:295 涉及麦克风流、WAV/base64 和播放对象；缓冲大小、队列上限及释放都是候选检查点。
- 任务 4 已整理音频生命周期、Live2D 空闲采样和前端延迟加载，但构建包变小、MCP 初始化变快都不能证明 RAM 已下降，见 INV-23。
- 当前还没有完整进程树的同条件 RAM 基线，不能把总占用归因于某一个库。

### 3.2 测量方法

使用 release 构建或明确标识的等价发布配置，避免把 Vite 热更新与开发工具开销算成发布版。首次模型下载单列；正常冷启动、模型已缓存的冷启动、暖启动分开。记录应用/依赖版本、系统与芯片、总 RAM、已启用模型与 MCP 列表、角色资产和测试脚本。

观测范围包含 Tauri、WebView/WebContent、Python、归属本应用的 MCP 子进程以及本地 TTS/模型服务。逐进程记录 RSS，配合 Instruments 的分配与 VM/footprint 观察，以及系统压缩内存、swap、内存压力；共享页和图形内存可能影响汇总，不能把 RSS 简单相加后当成精确独占内存。[Apple 内存测量](https://developer.apple.com/documentation/xcode/gathering-information-about-memory-use)

| 场景 | 建议采样 | 需要解释的结果 |
| --- | --- | --- |
| 启动到空闲 | 冷/暖启动各多次；空闲 10 分钟 | 首峰、稳定占用、模型预热带来的变化 |
| 纯文本使用 | 固定 20 轮、随后空闲 | 语音是否仍常驻；历史、工具结果是否持续积累 |
| 连续语音 | 正常播放、打断、再说、关闭麦克风 | 本地 ASR 峰值、音频队列、关闭后回落 |
| 切换角色与面板 | 连续 30 次切换，再稳定等待 | 旧纹理、RAF、监听器和音频上下文是否残留 |
| 长时运行 | 内测前做 2 小时与隔夜 soak | 增长斜率、压缩与 swap、线程/句柄/子进程变化 |
| 恢复与压力 | 睡眠唤醒、设备切换、模型失败、网络断开 | 是否重复加载、孤儿进程、重复任务和资源回收 |

每次优化用同机、同模型、同任务交替运行 A/B。小样本报告原始数据和中位数；只有足够样本才解释 P95。任务 4 的两组 MCP 数字不能被包装成统计稳定的整机结论。

### 3.3 候选优化顺序及代价

| 候选 | 预期解决的问题 | 代价与验证 |
| --- | --- | --- |
| 按能力启动模型 | 纯文本用户不需要一直承担语音模型占用 | 首次使用变慢；真实显示加载中，不能假置 ready |
| 模型空闲回收 | 停止语音后恢复常驻预算 | 需借用计数、并发保护和最短驻留时间，避免加载/卸载抖动 |
| 必要时隔离模型进程 | native allocator 不归还内存或模型崩溃影响主服务 | 进程退出便于明确回收；增加 IPC、启动成本和打包复杂度 |
| 复用向量、批量写入与有界缓存 | 减少重复编码和无界对象增长 | 缓存按用户/模型版本区分；记录命中率，不能牺牲隔离 |
| 资产与音频按生命周期释放 | 纹理、解码音频、长队列和后台采样 | 前端包大小、CPU、GPU 资源、RAM 分别测量 |
| MCP 按需连接及空闲退出 | 大量连接器常驻的子进程开销 | 首次工具延迟、重连风暴、取消后的清理 |
| 更小/量化 ASR 或其他本地后端 | 降低语音计算成本 | 对中文、专名、噪音和延迟做同语料评测 |
| 云端 ASR/embedding | 转移本地模型占用 | 网络、费用、授权数据流、离线能力都改变 |

faster-whisper 官方基准中，量化和 batch_size 都会改变内存与吞吐；CPU 基准使用的是指定 Intel 设备，不能移植为 Apple Silicon 承诺。[官方基准](https://github.com/SYSTRAN/faster-whisper)

CTranslate2 文档描述了删除模型对象释放资源，并为 Translator 提供加载/卸载方法。这不证明当前 Whisper 包装器支持相同接口，也不保证整个 Python 进程 RSS 立即回落。具体实现前要检查本项目依赖版本和持有关系。[CTranslate2 内存管理](https://opennmt.net/CTranslate2/memory.html)

建议先设计“轻量常驻 / 语音已准备 / 本地增强”三种运行档位。自用时先依据用户这台设备和语音习惯选默认档，再考虑其他硬件。用户看到能力和加载状态，内部资源策略按真实需求切换。改变现有四路 appReady 是独立产品与工程变更，须保留真实 boot marks，不能在代码瘦身名义下绕过。

### 3.4 可讨论的预算起点

以下是为了启动讨论提出的目标，**不是行业统一标准、当前实测或已批准发布门槛**：

- 参考设备先选 16 GB Apple Silicon；若要支持 8 GB，必须追加该档测试，不能用 16 GB 的通过替代。
- “轻量常驻”候选目标：无本地 ASR 常驻、标准角色资产下，归属应用的内存指标约 800 MiB 以内；本地语音活跃档候选峰值约 2.5 GiB 以内。先取得基线，再决定能否达成、是否调整默认档位。
- 30 次切换/打断后稳定 10 分钟，相比同一状态起点的增长候选上限为 max(50 MiB, 起点的 10%)；出现持续增长必须解释，不能仅因低于上限就忽略。
- 任何降低 RAM 的方案，同时报告首次语音延迟、日常任务正确率、CPU/能耗与崩溃情况。不得把云端费用转移或明显体验退化当成无代价优化。

### 4.2 区分六类数据与一个程序知识层

| 类型 | 建议保存的位置和生命周期 | 进入模型上下文的方式 |
| --- | --- | --- |
| 对话原文 | 可检索历史；明确保留与删除规则 | 近期窗口或按需读取原始证据 |
| 工作状态 | task/step/attempt 等结构化状态，任务结束后归档 | 当前目标、已做动作、未完成项和恢复位置 |
| 用户事实与偏好 | 带来源、时间、有效期、范围和版本的记录 | 少量稳定偏好 + 本轮相关事实 |
| 文档与外部知识 | 来源文档、块索引、权限、版本 | 先按范围检索，再展开必要证据 |
| 角色设定与私有经历 | 人设配置、独立角色作用域 | 与事实/操作结果分层，不能冒充用户经历 |
| 提醒与承诺 | 有到期时间、状态、投递与回执的任务系统 | 当前相关任务摘要；执行靠调度系统 |
| 可复用流程 | 版本化技能/工作流，含适用条件、权限、验证与回滚 | 先暴露简短目录，匹配时加载正文 |

记忆并不需要全部写入 system prompt；长期存储也不等于每轮读取全部。上下文工程的核心是让当轮看到足够且相关的证据，长任务则需要压缩与可恢复状态。[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 4.3 写入可靠性：先让“记住了”有凭据

建议给提取批次保存范围、状态、尝试次数、最后错误、下一次重试时间和幂等键。区分“没有值得记住的事实”“解析失败”“服务超时”“写库失败”，不能都以正常空结果结束。

设计选择有两种：

- 简单串行方案：当前批失败后有限重试，成功或进入持久失败清单后再推进游标。
- 可并行方案：扫描游标可前进，但每个失败批次必须先持久化为独立任务，重试与扫描解耦；另有提交/完成状态，不以扫描位置代表成功。

单机首轮更适合简单、有界的方案。用事务、唯一约束及来源批次标识避免重复写入；embedding 失败单独进入待回填状态，文本仍可通过关键词等路径找到。重启、重复请求和补偿执行均要保留可解释的状态。

对事实增加 supersedes/有效时间等关系时，先处理有明确实体和字段的更正。用户说“以前住 A，现在住 B”，应保留历史且令当前查询返回 B；不能用向量相似度当作语义覆盖依据。删除还要传播到向量/全文索引、缓存、摘要和可恢复备份的保留策略，避免旧记录再次进入模型。更细范围应按用户确认的共享规则逐步迁移，不直接把所有现有用户事实改成角色私有。

### 4.4 检索：从长度门槛走向任务证据

建议路由结果至少区分：近期信息已足够、历史记忆、授权文档、实时外部工具、需要用户澄清。规则可先覆盖明确场景，只有不确定时增加模型判定，并把判定开销计入总成本。

“上次那件事呢”可能很短却依赖历史；“今天心情不错，随便聊聊……”可能很长却不用召回。当前长度门可作性能辅助信号，不能承担最终检索决策。

建议先比较：

1. 现有向量 Top 5 基线。
2. 元数据过滤 + 全文检索。
3. 元数据过滤 + 全文/向量混合排序。
4. 仅在证据不足时，先找话题摘要，再展开原文的两阶段检索。

先做权限/用户/角色/时间过滤，再检索；高风险范围同时校验读取结果。允许“没有找到可靠记录”的空结果。长期记忆规模未证明需要独立向量数据库，先复用已有 SQLite 和已存向量。只在实测吞吐、索引更新或多用户部署成为限制时引入外部服务。

SQLite FTS5 的分词必须用中文样例测试；trigram 全文查询对少于三个 Unicode 字符的子串存在限制。“张三”“那事”等短词需要补充分词、实体索引或受控回退，不能把英文检索表现直接套给中文。[SQLite FTS5](https://www.sqlite.org/fts5.html)

评测至少包含：短指代、跨会话旧事、明确纠正、过期事实、互相矛盾、无答案、删除后召回、角色私有经历、实时信息、中文专名。除 Recall@k 外，记录无关召回率、正确拒答、证据引用正确率和每次检索耗时。

### 4.5 上下文预算与费用治理

建议 Context Builder 统一记录每层 Token、优先级、来源和截断原因；保留完整 tool call/result 配对，不能为了预算截断成无效协议。当前消息、已确认约束和执行状态优先；附件全文和巨大工具输出用索引/分页/按需展开。

一个供评测的普通任务预算示例：

| 层 | Token 上限示例 |
| --- | ---: |
| 平台规则 | 800 |
| 角色表达 | 400 |
| 稳定用户偏好 | 400 |
| 当前任务与状态 | 800 |
| 近期原文 | 4,000 |
| 旧对话摘要 | 1,000 |
| 召回证据 | 2,000 |
| 当前工具 schemas | 2,000 |
| 工具结果 | 2,500 |
| 当前用户输入 | 2,000 |
| 合计上限 | 15,900 |

这只是选定模型支持足够上下文时的实验档位，未建议立即把现有摘要预算从 2,000 改成 1,000。各层不用填满；长文档、图像和复杂任务有单独档位。还须预留输出与协议空间，用模型对应 tokenizer/供应商统计校准，避免用“字符数÷固定常数”做账单依据。

缓存单独测量：稳定前缀、工具顺序、模型设置和有效缓存边界都会影响复用。改变工具集合可能减少上下文却降低缓存命中，因此同时比较每个成功任务的总费用和延迟。供应商缓存规则各异，不把某家 API 参数直接发给所有模型。[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

建议单任务记录所有模型调用、输入/缓存/输出 usage、ASR/TTS、重试、后台提取和技能审查成本；设置可解释的最大步骤、耗时和费用预算，达到预算后保存进度并交回用户。提示词版本、模型版本、工具目录版本要可追踪。

成本公式：

每个成功任务成本 = 同一统计周期内所有任务尝试及后台工作的模型费、语音费、工具费、失败重试与分摊运行成本总和 ÷ 该周期成功任务数。失败任务的开销也计入分子；没有成功任务时报告总支出与失败情况，不计算该比值。

演算示例（价格完全是假设，不是任何供应商报价）：每月 30 天 × 每天 20 个任务 × 每任务 3 次调用 = 1,800 次；若每次输入 6,000 Token、输出 500，假定输入每百万 2 元、输出每百万 8 元，无缓存，则纯 LLM 费用约 28.8 元/月。输入涨到 15,000 时约 61.2 元/月。语音、搜索、后台反思和可能的托管服务费用尚未计入。个人预算应以全链路实际 usage 校准。

当前自用优先沿用用户已有的模型账户，提供个人月预算、逐任务成本和超额前告警。若未来做托管额度，再增加账户计费和服务运营。先为少量已验证模型维护完整工具能力，其他模型可保留实验入口。

### 4.6 工具选择和执行契约

建议保留 registry 为能力真源，并提供四层信息：

1. 用户和任务当前有权使用的能力目录。
2. 按任务选中的少量 schemas；以工具族为单位保持稳定。
3. 相关工具的必要操作说明，按需注入。
4. 执行时再次验证真实工具名、权限、参数、目标对象和确认状态。

低置信度时扩大可见工具或搜索目录，不能因分类器没选中就错误宣布“不支持”。工具输出应带状态、来源、时间、分页游标和可核验外部标识。官方函数调用与工具设计材料都强调清晰参数和减少工具歧义；具体初始数量须用 Momo 任务集确定。[Function calling](https://developers.openai.com/api/docs/guides/function-calling)、[工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)

MCP 连接成功不是权限授权。外部网页、邮件和工具返回内容只能作为数据；动态工具目录也不允许绕过执行时的校验。远端 OAuth token 的受众、scope 和撤销分别处理，不能将 token 任意透传给另一服务。[MCP 安全实践](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

### 4.7 半双工、可打断与全双工

| 级别 | 用户实际体验 | Momo 的建议 |
| --- | --- | --- |
| 轮流说话/按键说话 | 等对方说完，稳定且易理解 | 保留为可靠回退和可选择模式 |
| 可打断的语音对话 | AI 说话时用户开口，系统及时停止并接住后续 | 优先补齐端到端取消、误打断恢复、文本与音频一致性 |
| 全双工交互 | 双方重叠发声，区分附和、插话、停顿和真正抢话 | 在重叠语音与扬声器场景证明价值后进入产品默认 |

当前 getUserMedia 使用 audio: true，播放主要以完整 WAV/base64 段进入队列，打断有音量阈值路径；本次没有验证当前设备的回声消除质量。请求 echoCancellation 约束并不等于目标 WebView 和设备已经有效消除回声。[MDN 约束说明](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)

建议先明确语音状态和事件顺序：采集 → 识别 → 轮次结束判断 → 生成 → 播放；打断同时携带 turn/generation 标识，停止播放、取消生成并拒收旧轮迟到音频。取消发出后，已在外部系统发生的写操作仍要核验，不能以“语音取消了”推定动作未执行。

LiveKit 把回合结束、打断、误打断恢复、预先生成及音频预处理分别配置；这一拆分适合借鉴。是否引入其 SDK，应在独立语音原型中比较部署和资源成本。[LiveKit turn tuning](https://docs.livekit.io/agents/logic/turns/tuning/)

原生实时语音可以减少流水线环节，但模型供应商、音色控制、转录与工具执行方式会改变。server VAD/semantic VAD 处理的是轮次判断，单独启用不能证明全双工质量。[OpenAI VAD](https://developers.openai.com/api/docs/guides/realtime-vad)

评测覆盖耳机/外放、安静/噪音、中文与中英混合、长停顿、咳嗽、旁人声音、用户说“嗯”与“停一下”、设备切换和断网。记录语音结束到首音频的延迟、打断到停止播放延迟、误打断/漏打断、被吞掉的词、最终 transcript 与实际播放内容差异，以及每分钟费用。没有这一组数据，不把“可以持续开麦”写成全双工已完成。

### 5.2 MaiBot：人设强在行为和表达组织

官方把 personality、behavior_style、reply_style 分开，也允许按时间/聊天范围调整参与程度。表达学习可分别控制学习和使用范围，并有 AI 自审与人工精选开关；当前文档的人工精选限定默认关闭。由此可借鉴的是明确谁在说、何时说和如何说，以及可管理的表达样例，而非无限增大人设文字。[MaiBot 配置](https://docs.mai-mai.org/manual/configuration/bot-config)

对 Momo 的设计建议：

- 保留 Persona 身份与稳定表达；把主动参与策略和当前任务状态独立管理。
- 助手卡中任务结论、时间、动作状态由真实证据决定；角色负责措辞、语气、节奏。

- 工作专注时减少主动表达，失败时直接说明原因；闲聊中允许更自然的短句与停顿。不要每次任务都额外调用一遍昂贵“人格导演”。

A_Memorix 文档给出范围过滤、混合检索、记忆生命周期和向量模型指纹管理；它也提示更换模型/维度会改变既有向量的解释方式。这对 Momo 的存储版本与迁移设计有参考价值，不能只复制检索调用。[A_Memorix 配置](https://docs.mai-mai.org/manual/configuration/amemorix-config)

### 5.3 Hermes：学习可复用流程和按需加载

| Cron | 定时任务可用新会话，也有不调用 LLM 的脚本模式 | 固定提醒与已确定动作直接执行，开放问题才用模型 |
| 后台复盘 | 可配置启停、模型及输入预算 | 独立计费与频率上限；后台调用不能悄悄吞掉交互预算 |

来源：[Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)、[Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/)、[Tool Search](https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-search/)、[Cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron/)。

Hermes 的“成长”在这些机制中体现为记忆和流程资产更新，不能据此宣称 Momo 已做权重微调。模型微调只有在固定评测持续暴露风格/行为缺口、具备获授权的高质量训练样本、明确托管和回滚方式时才值得另立项目；本轮未发现立刻开展训练的依据。

### 5.5 商业复用的边界

仓库许可证与第三方模型、角色资产、声音、平台连接条款分别登记。MaiBot 的 GPL-3.0 与 Hermes 的 MIT 不是同一义务；借鉴设计、复制代码、修改分发和作为外部服务使用也不是同一种行为。若复用代码，应锁定 commit 并审查相应 LICENSE、NOTICE、依赖和发行方式；GPL 不能被简单表述为“不能商用”。本轮建议先把机制转化为 Momo 的独立设计，不以此报告代替具体发行许可审查。

Momo 允许加载 Live2D 模型，商业发行时尤其要核对是否属于官方定义的 Expandable Applications。Live2D 对该类别有单独审查与发布协议；不能因使用 PixiJS 或开源显示层就推断 Cubism 和角色资产都已获商用许可。[SDK 发布许可](https://www.live2d.com/en/sdk/license/)、[Expandable Applications](https://www.live2d.com/en/sdk/license/expandable/)

### 6.2 架构选型建议

| 选项 | 合适条件 | 对 Momo 的当前判断 |
| --- | --- | --- |
| 现有 FastAPI + 显式状态 + SQLite | 本地单用户、有限任务与连接器 | 优先验证；迁移量最小，但恢复和幂等必须自己实现 |
| LangGraph 的持久化编排 | 中断/恢复与步骤状态越来越复杂，需要图状态和持久 checkpoint | 可挑一个复杂任务作对照原型，再决定引入范围 |
| 托管 Agent SDK/运行平台 | 团队愿意采用相应供应商协议与部署方式 | 核对工具兼容、可观测、迁移成本和本地桌面控制边界 |
| Temporal 类持久工作流 | 云端长任务、跨设备、多个 worker、长期恢复成为核心需求 | 后续部署选择；首轮桌面内测没有证据需要这套服务 |
| 独立向量服务 | 规模、多用户隔离或索引更新实测超出本地方案 | 以检索质量和资源数据触发选型 |

LangGraph 将会话 checkpoint 与跨会话 store 区分，并提示内存 saver 在进程重启后丢失；引入框架本身不等于状态已经持久可靠。[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

Temporal 提供持久执行与恢复的基础设施，但外部写动作仍需定义幂等和恢复语义；选择它会改变部署和运维成本。[Temporal](https://docs.temporal.io/evaluate)

### 6.3 观察与评测的最小集合

建议给用户任务分配 trace_id，关联模型调用、检索、工具、确认、重试、语音和最终外部结果。最初可使用本地结构化记录，格式留出接入可观测平台的空间；不先建设昂贵平台。日志正文和截图默认最小化保存，诊断导出由用户选择。

固定评测集合同时检查：最终状态、来源是否正确、权限是否遵守、语言是否清楚、总成本与延迟。模型裁判适合辅助评表达，完成/重复写入等应由外部状态或确定性检查判断。Agent 输出有波动，同一用例需多次尝试，不能只选择最好的一次。[Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

若将来走企业/团队产品，再追加：身份与租户边界、管理员策略、SSO/集中授权、成员离职撤销、团队共享数据范围、组织审计、数据驻留/保留、服务支持和事件处置。第三方服务可用区域应按当前自用环境核对；对外发行地区与相应要求在实际决定发布时专项评估。

### 7.2 候选质量门

以下数值是供选择自用验收规格的起点；需用阶段 A 的结果校准，不能当成已达到的商业承诺。目标是每次改动后有依据判断是否更好用。

| 维度 | 内测候选目标 | 测量要求 |
| --- | --- | --- |
| 核心任务完成率 | 对已限定支持范围，首轮争取 ≥90%；稳定日用阶段讨论 ≥95% 或更高 | 固定任务集，多次试验，报告样本数与失败类型；重大写操作单独验收 |
| 严重行为 | 不接受越权写入、重复不可逆动作、假完成、跨用户/私有范围泄露 | 故障与攻击样本必须覆盖；测试零事件不证明真实世界零风险 |

| 交互延迟 | 支持的模型/网络下，暖态文本首响应 P95 候选 ≤3 秒 | 本地排队、网络、供应商分别记录；工具任务总时长另列 |
| 语音 | 结束到首音频 P95 候选 ≤2.5 秒；确认打断到本地停播候选 ≤300 ms | 开口到检测的延迟另测，不能只公布较短的后半段 |
| 资源 | 采用第 3.4 节经基线校准的档位预算 | 同时报告冷启动、空闲回落、长时运行与首轮代价 |
| 提醒 | 计划与投递状态可靠，重复/漏投可解释 | 仅在声明的运行条件下衡量准时率；睡眠/退出/关机分类 |
| 版本与恢复 | 更换工作目录、版本切换、数据库恢复和撤销授权都能走通 | 隔离测试库先验证，真实系统通知/权限另验；对外发布再测完整安装升级 |
| 成本 | 每个成功任务成本可解释，个人月费用受预算约束 | 所有后台调用、重试、工具与语音纳入 |

建议首个评测集至少覆盖常见成功、边界请求、外部服务失败、重启/重复执行、权限变化、恶意外部指令、长会话、删除/更正和语音打断。例：60 个正常/边界场景 + 40 个故障/权限/恢复场景；随机模型路径每例跑 3 次。这个规模用于建立回归习惯，不能估计极低概率事故或证明市场可行性。

### 7.3 与 AI coding 流程衔接

采用一条可追踪的链：用户原话 → 场景卡 → 版本化单项 PRD → 关键设计决策 → 小批实现 → 自动回归 + 真实任务评测 → 用户验收 → 发布记录。

PRD 可以变化，但每次变化应记录“为什么、影响哪些验收项、哪些已实现内容需要迁移”。研究建议、待确认需求、正在实现和已验收分别标记。模型、提示词、记忆路由或工具集合的改动都可能改变产品行为，需要质量对照，不能仅用编译通过判定完成。

## 11. 低 Token 记忆与闲聊处理细化（2026-10-14）

用户追加的问题：如何少用 Token 找到对应记忆，避免每次通读；闲聊、随口提问与顺带提到的信息如何处理。以下是候选设计，尚未实施；不改变任务 4 的行为保持边界。

### 11.1 当前行为：区分模型阅读与本地扫描

重新核对 backend/memory/long_term.py:289：当前读取用户/可选角色范围的记忆，在本地对已存向量逐条计算相似度；chat.py:1612 常规取 Top 5，再进入仲裁与上下文准备。因此不是把整个库交给聊天模型阅读。当前向量编码用本地 sentence-transformers，主要承担本地计算/RAM 成本；最终注入文本、提取与摘要等模型调用才分别产生相应 LLM Token。

需要分开测量：检索本地耗时/峰值内存、最终注入 Token、查询改写与提取/摘要的额外调用成本、召回正确率。单纯把精确向量循环换成某个“向量数据库”不保证免全扫，需确认真实索引和查询计划；小规模时精确检索可能更省维护和索引常驻资源。

### 11.2 读路径：先定位，再读取必要证据

建议流程：当前消息与近期话题 → 判断证据需求 → 按权限/用户/角色/时间范围检索 → 少量候选 → 读取证据 → 按 Token 预算组装。

1. **近期就能回答：**直接使用近期窗口和当前话题指针，不额外搜索长期库。明显问候无需召回；消息短不能作为跳过历史的唯一理由。
2. **明确实体/字段：**例如宠物名字，使用结构化实体与字段索引，取当前有效事实及来源。先验证实体归属，不能把朋友的猫归到用户名下。
3. **记得措辞或话题：**用全文倒排索引找事件/对话片段，支持日期和会话限制；提问本身可作为检索线索。SQLite FTS5 提供 MATCH、排序和片段能力，但中文分词、两字专名与 trigram 短查询限制需评测。[FTS5](https://www.sqlite.org/fts5.html)
4. **模糊回忆或换说法：**使用语义检索，与全文命中合并并去重；规模需要时再选经过本机验证的近似向量索引。不要只在关键词命中内做向量排序，否则同义表达可能永远进不了候选。近似索引的额外 RAM 与漏召回也要测。
5. **“上次那个呢”：**先结合最近话题、显式项目/人物和时间线索，形成短查询；必要时进行一次有预算的查询改写。多个旧事同样合理时询问用户，不把最近一次自动当作唯一正确答案。
6. **渐进读取：**检索后先用简短标题、日期、事件/事实与来源 ID 定位，按需加载原文周边。普通精确查询由程序直接返回必要证据；复杂问题才让模型调用搜索/展开工具，避免每次都多一轮 LLM 往返。结果不足时允许受预算约束的扩大检索或澄清。

作为实验起点，可比较每次本地取 10～30 个候选，最终按相关性和去重选择约 2～5 条；普通问答的新增记忆上下文试用 300～800 Token 的软预算。条数和预算均非固定产品承诺，回答所需证据优先，长时间线任务单独预算。SQL LIMIT 只限制结果数，不证明底层没有全扫；候选列表也不应全部注入 prompt。

例：用户问“我家猫叫什么”，模型只需收到“用户的猫名为 Mochi；来源 turn 123；用户直接陈述；当前有效”等必要证据，无需整段历史。此例仅说明结构，未测实际 tokenizer 数量。

Hermes 将小量常驻记忆和历史搜索分开，可作机制参照；这里建议保持 Momo 现有 SQLite，并设计自己的权限与证据格式。[Hermes Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)

### 11.3 写路径：随口说也可能重要，随口问不等于个人事实

| 用户表达 | 候选处理 | 以后如何回忆 |
| --- | --- | --- |
| “哈哈”“早呀” | 按历史保留设置进入原文；无需逐条生成长期事实或摘要 | 在会话原文范围内可查，默认不作为长期事实召回 |
| “今天好累” | 最近上下文中的临时状态；必要时带有效期保存 | 当天交流可承接，不据一次表达推断长期性格/健康状态 |
| “猫粮哪种好？” | 保留问题及后续对话为事件线索 | 可回答“你曾问过猫粮”；不能推断“用户养猫” |
| “我家 Mochi 又把水杯打翻了” | 可提取明确宠物名称/归属；具体物种仍看原文是否明确，事件单独归档 | “Mochi”可定位稳定事实；“打翻水杯”可定位那次聊天 |
| “我朋友的猫叫 Mochi” | 明确第三方实体关系，不写成用户宠物 | 按朋友/猫检索；没有明确身份不强行合并同名实体 |
| “假如我搬去上海……” | 标注假设，保留在对话/话题记录 | 不能更新用户当前住址 |
| “最近在考虑买相机，还没决定” | 保留带时间的考虑中事件或进行中话题 | 后续问“我上次想买什么”可回忆；不升级成永久爱好或已购买 |
| “周五提醒我交材料” | 经所需信息/授权确认后进入结构化任务；保留关联事件 | 调度执行与投递状态靠任务系统，不能仅靠记忆召回 |
| “之前说错了，我现在住杭州” | 当前事实更正，旧值有历史边界，保留原始证据 | 当前查询返回新值，历史查询可解释变化 |
| “别记这件事” | 按约定的记忆退出/删除范围执行 | 不再提取或召回；聊天原文、备份是否删除要明确说明其独立范围 |

当前 backend/prompts/memory_extraction.py 已要求提取单次、随口但明确的稳定事实，并排除闲聊问句/临时情绪。这是已有提示词约束，不等于已全面通过效果评测。其 confidence 是模型自评，不能当成校准概率；重复出现也不自动等于真实。

### 11.4 防止“长期事实没存，所以聊天全忘了”

建议维护三种可检索材料：① 稳定事实与偏好；② 带时间的话题/事件片段及短摘要；③ 按保留设置保存的对话原文。临时工作状态和提醒另走结构化状态。未升格为长期事实的闲聊仍可通过事件或原文找到；保留历史不等于每轮加载历史。

对话分段可以由话题变化、时间间隔或 Token 上限触发；保留用户/助手说话者、问句/断言/假设/引用性质、来源 turn 范围和时间。来源原文是复核依据，摘要用于定位；摘要遗漏时可回查原文。不要将相似度、访问次数或摘要中的措辞自动当成事实可信度，也不能让被反复召回的错误记录自行提高可信度。

写入尽量只处理新增或修改内容，按批次/话题结束合并；索引与 embedding 只更新受影响片段，并标注版本。显式“记住”或更正优先更新当前会话状态，再可靠持久化；后台失败有记录与重放。避免每条问候调用模型，也避免每轮重新总结全部历史。简单规则只跳过明确无信息内容，不用激进过滤漏掉随口事实。

费用需把异步提取、摘要、查询改写、检索/展开额外轮数一起计入。稳定画像也按相关性与预算装配，不默认全量常驻。缓存按用户/角色/数据版本隔离；更正、删除和过期触发失效。
